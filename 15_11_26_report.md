# Sequential Realtime Visualization Report

Date: 2026-11-15
Project: Load-cell ADC R-DAE pipeline

## 1. Purpose of this update

The visualization requirement was changed from one combined dashboard to a sequential realtime workflow. Each intermediate procedure must be visible in its own window, and the next procedure must start only after the current window is closed.

The implementation is in:

- `loadcell_sequential_visualization.py`

The original single-dashboard implementation remains in:

- `loadcell_realtime_visualization.py`

## 2. Final workflow

The sequential viewer uses one ADC file and processes the data in this order:

1. ADC input and ADC-to-weight interpretation
2. Chronological train/validation/test split
3. Moving-average filtering and residual analysis
4. Normalization and temporal window construction
5. Recurrent denoising autoencoder training
6. Encoder/bottleneck output and encoding latency
7. Total filtering and R-DAE reconstruction
8. FCM feature clustering
9. Health/degradation trend
10. Final metrics and generated output files

Each stage has its own visualization window.

## 3. Multiple-window issue and correction

### Previous behavior

The viewer enabled Matplotlib interactive mode globally with `plt.ion()`. Because of that, calling `plt.show(block=True)` did not always behave as a strict wait operation. A later stage could begin while the previous stage was still visible, resulting in multiple windows appearing together.

### Correction

The stage controller now:

1. Saves the current stage image.
2. Temporarily disables interactive mode.
3. Shows the current figure.
4. Blocks execution until the user closes that figure.
5. Restores interactive mode.
6. Allows the next stage to start.

The R-DAE training window uses the same blocking behavior after training finishes.

Therefore, the intended sequence is now:

```text
Open Stage 1
    |
User closes Stage 1
    |
Open Stage 2
    |
User closes Stage 2
    |
Open Stage 3
    |
...
```

## 4. Realtime drawing behavior

The windows are not simply plotted after all computation has finished. The data is progressively revealed while each stage is active.

### Stage 1: ADC input and weight interpretation

- Raw ADC values are plotted progressively.
- A provisional relative-weight curve is shown using:

```text
relative_weight = ADC_value / median(ADC_values) * 535 g
```

This is not a calibrated physical conversion. The `535 g` value comes from the filename metadata and is used only as a reference scale.

### Stage 2: chronological split

- The raw signal is shown with colored training, validation, and test regions.
- Window counts are reported for each region.

### Stage 3: filtering

- Raw ADC and moving-average reference curves are progressively drawn.
- The raw-minus-reference residual is shown.
- The residual demonstrates how much variation the moving-average reference removes.

### Stage 4: normalization and windowing

- A normalized noisy and target window is shown.
- A matrix view reveals the temporal windows entering the LSTM.
- Values are scaled to `[0, 1]` for stable neural-network training.

### Stage 5: R-DAE training

- The training window opens before model training finishes.
- Train MSE and validation MSE update after every epoch.
- The user can observe whether the model is learning and whether validation loss follows training loss.

### Stage 6: encoding latency

- The latency window opens before all test windows are encoded.
- A latency bar is added after each encoder batch.
- Bottleneck feature traces grow as encoded batches become available.
- The final window reports total latency and average latency per test window.

### Stage 7: total filtering and reconstruction

- The noisy test signal and pseudo-clean target are displayed first.
- The R-DAE output line grows after each prediction batch.
- Final metrics compare noisy input and reconstructed output against the moving-average target.

### Stage 8: FCM clustering

- The clustering window opens with empty point content.
- Feature points appear progressively.
- Red `X` markers identify cluster centroids.
- The plotted features are mean and standard deviation of reconstruction error.

### Stage 9: health trend

- Fuzzy severity, reconstruction-error severity, and smoothed degradation curves are progressively revealed.
- The state plot shows Healthy, Warning, and Degraded threshold states.

### Stage 10: final summary

The final window reports:

- Input file
- Sample count
- Train, validation, and test window counts
- Total encoding latency
- Per-window encoding latency
- Noisy and reconstructed MAE
- Health trend slope
- Monotonicity ratio
- Health-state counts
- Output file locations

## 5. Main functions added or updated

### `animate_axis_lines`

Reveals one or more line plots in chunks while the figure is open.

### `animate_image`

Reveals normalized-window matrix rows progressively.

### `show_stage`

Controls the stage lifecycle. It saves the image and blocks until the current window is closed.

### `display_adc_to_weight`

Shows raw ADC values and the provisional relative-weight interpretation.

### `display_split`

Shows chronological split regions and window counts.

### `display_filtering`

Shows the moving-average reference and filtering residual.

### `display_normalization`

Shows normalized input/target windows and the LSTM input matrix.

### `LiveTrainingWindow`

Updates train and validation loss after each training epoch.

### `display_latency`

Measures encoder latency batch by batch and reveals bottleneck outputs in realtime.

### `display_filtering_output`

Runs reconstruction batch by batch and progressively draws the R-DAE output.

### `display_clusters`

Progressively reveals FCM feature points and centroids.

### `display_health_trend`

Progressively draws health severity and state trends.

### `display_summary`

Shows final output metrics and generated file paths.

## 7. How to run

### Interactive sequential mode

```bash
python3 loadcell_sequential_visualization.py
```

The default input file is:

```text
adc_data/535g20250502pm427ms20hz50.txt
```

Close the current window to start the next stage.

### Headless validation mode

```bash
MPLBACKEND=Agg python3 loadcell_sequential_visualization.py --epochs 1 --no-show
```

This saves all stage images without opening GUI windows.

### Full training mode

```bash
python3 loadcell_sequential_visualization.py --epochs 25
```

The default model configuration uses 25 epochs.

## 9. Interpretation of outputs

The expected output of the pipeline is not only one final number. It is a sequence of intermediate products:

```text
Raw ADC signal
    -> pseudo-clean filtered reference
    -> normalized temporal windows
    -> trained R-DAE
    -> denoised/reconstructed test signal
    -> bottleneck feature matrix
    -> FCM cluster assignments
    -> health/degradation indicator
```

The purpose of the visualization is to make each transformation observable and explainable.

## 10. Important limitations

### 10.1 ADC-to-weight conversion is provisional

The input files contain raw ADC counts. The `535 g` value is an applied-load condition from the filename. A calibrated grams output requires independent calibration measurements at multiple known loads.

### 10.2 Pseudo-clean reference

The current clean target is a 31-sample moving average of the same raw ADC recording. It is useful for developing the pipeline but is not independent physical ground truth.

### 10.3 No failure labels

The dataset does not include failure time, degradation labels, or RUL labels. The health trend cannot currently be used to claim RUL accuracy.

### 10.4 Health state thresholds are exploratory

The Healthy, Warning, and Degraded thresholds are fixed normalized-score thresholds. They have not yet been calibrated using expert labels or known failure events.

### 10.5 Reconstruction metrics are target-relative

The MSE and MAE values compare against the moving-average pseudo-clean target. They should not be interpreted as physical denoising accuracy until an independent reference is available.

### 10.6 GUI dependence

Interactive sequential windows require a graphical Matplotlib backend. The `--no-show` mode is available for servers, automated checks, and headless environments.

## 11. Recommended professor explanation

> The original pipeline displayed several results together in one dashboard. We changed it to a sequential realtime visualization system. Each processing stage opens in its own window and updates while its data is being generated. The first stage shows the raw ADC signal and a provisional weight interpretation. The next stages show chronological splitting, filtering, normalization, window formation, R-DAE training, encoder latency, reconstruction, FCM clustering, and health-trend generation. After the user closes one window, the next stage begins. This makes the complete intermediate data flow visible instead of showing only the final result. The current system demonstrates the software pipeline successfully, while calibrated weight estimation and RUL prediction remain future tasks because independent calibration and failure labels are not yet available.

## 12. Final status

The separate-window realtime visualization requirement is implemented and validated.

The main correction was not a change to the R-DAE algorithm. It was a change to visualization control flow:

- Open one stage
- Update that stage in realtime
- Save the stage output
- Wait for the user to close the stage
- Start the next stage

This now gives a controlled, presentation-ready explanation of the complete ADC-to-health-feature pipeline.
